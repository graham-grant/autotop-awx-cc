# Production rebuild: validation method

Created 2026-10-31 · Status: proposed; the stage 1 kit is built and tested · Applies to every stage of the [production rebuild roadmap](production-rebuild-roadmap.md)

## The problem

Every line of code that runs in production is regenerated by Microsoft Copilot from written instructions. The production network is segregated: no file, log or facts JSON can leave it. The only thing that comes back is what Jon reads off a job and passes on.

Two things have to be proved anyway:

1. **The rebuild behaves exactly like this repository.** Same data types, same JSON keys in the same order, same values, same messages, same exit codes. Not similar: identical.
2. **Collection never changes a device.** The command allowlist has to work on live gear the first time, and every layer of the read-only guarantee has to be present and working before the first device is contacted.

## Principles

- **The reference code is the only source of truth.** Every expected result is produced by running this repository's code, never written by hand. If the reference changes, the expectations are rebuilt from it, and a test fails until they are.
- **Compare exactly.** Results are compared as canonical JSON with key order kept. `1`, `1.0` and `true` are different; `null` and `""` are different; a list in a different order is different. "Close enough" doesn't pass.
- **Data goes in, counts come out.** What is carried into production is instructions and test data. What comes out is pass counts, rule names, JSON paths and digests. Every input in the kit is synthetic, so a failure line that quotes one is safe to share.
- **Check the read-only safeguards offline, never against a device.** Everything that tests a refusal, a confirmation prompt or a timeout runs against a fake device. Real devices only ever see the 13 planned commands.
- **The checker is checked too.** The runner has to catch deliberately wrong expectations, and the facts checker has its own vectors, so a broken validator can't report a pass.

## Layers

| Layer | Runs | What it proves | Comes back |
| --- | --- | --- | --- |
| 1. Conformance kit | Offline, any time; also play 1 of every collection job | Every function, constant, message, policy decision and session behaviour matches the reference exactly | `RESULT PASS 859/859 kit <digest>` |
| 2. Unit tests | Offline | The rebuild's own tests pass on the execution environment's Python | `Ran N tests ... OK` |
| 3. Structure checks | Offline, inside the kit, plus a short manual review | Only the expected functions write to a device or start a process; only standard-library imports | part of the kit result |
| 4. The plan | Play 1 of every collection job | The exact commands that will be sent, checked against the policy before any device is contacted | the plan text, which must match the instructions |
| 5. Pre-contact gate | Play 1 of every collection job | The code on this execution environment passes the kit; otherwise no device is contacted | job stops with the kit's FAIL lines |
| 6. Live checks | After each collection | Every line sent was planned and allowed; the configuration didn't change; each facts file has exactly the reference structure | `audit:` line, `CHECK` line |
| 7. Fingerprint | After each collection | The shape of real data (counts, types, allowed values) looks right for each device family | `FINGERPRINT` block |
| 8. Device-side record | Canary runs | The device itself received only what the job log says | Jon's confirmation |
| 9. Lab comparison (optional) | If a lab can run both versions | The two versions write the same facts for the same device | `compare:` line |

## Layer 1: the conformance kit

A kit is one JSON file per stage (`conformance/stage1/kit.json`). It holds vectors: something to run, and the exact result the reference produced. `conformance/build_kit.py` builds it by running every vector against this repository. `conformance/run_kit.py` runs it against whatever code is in the repository it sits in, and is itself rebuilt by Copilot from the stage 1 instructions.

Stage 1 has 859 vectors in 13 sections:

| Section | Vectors | Covers |
| --- | --- | --- |
| `constants` | 56 | Every safety-critical constant, character for character: the deny list, the pipe filters, every regular expression in the policy, the session (pager, password, confirmation and CLI prompt patterns) and the IOS parser, the command lists, credential variable names |
| `structure` | 23 | Which functions call `os.write`, `self._send`, `pty.fork`, `os.execvp` or any network or process call, in every stage 1 file; and that every import is standard library or the project's own |
| `platforms` | 135 | Platform names and aliases, which platforms have a driver and a policy, transports, command tables |
| `policy` | 418 | The read-only policy's decision and exact message for 418 commands: the commands collection uses, other `show` shapes, every deny-listed verb and its abbreviations, pipes that write files, chained filters, look-alike Unicode, invisible and control characters, newlines, stray spaces, `?`, session words, non-strings, and platforms with no policy |
| `plan` | 17 | The exact command list and plan for each platform, including refusals for platforms not in this stage, and the printed plan |
| `helpers` | 59 | MAC and interface-name normalisation, error-output detection, the config-change marker |
| `parsers` | 53 | Every IOS parser on every fixture and on edge cases |
| `records` | 16 | Whole schema 2 records built from six devices' output, plus empty, unknown-platform and alias cases |
| `audit` | 17 | `audit.verify()` on clean and broken audit records |
| `session` | 13 | Live sessions against the fake device: in-band login, pagers, wrong passwords, a refused command never reaching the device, a newline-smuggled second command, no policy means nothing is sent, a confirmation prompt cancelled with Ctrl-C and the session abandoned, a timeout cancelled before the next command, a refused paging command |
| `collect` | 14 | Whole `collect.py` runs against the fake device: the audit equals what the device received, a config change exits 3, a refused command stops before connecting, credential order, no credentials, unsupported platforms |
| `check_facts` | 34 | The facts checker itself: one good record and one mutation per rule |
| `selftest` | 4 | Deliberately wrong expectations; the runner must report each as a mismatch |

The kit is identical when built on Python 3.9 and 3.13, so a result from the production execution environment can be compared directly.

**How results are compared.** Each result is converted to plain JSON (tuples become lists; regular expressions become their pattern text and flags; bytes are kept as bytes) and compared as `json.dumps(value, ensure_ascii=True, separators=(",", ":"))`, key order kept. Type differences are reported, not coerced. A failure prints the vector id, the JSON path of the first difference, and the expected and actual values there.

**Per-step checks.** `run_kit.py --section NAME` runs one section, so each Copilot step is checked as soon as it's written. A stage is only accepted on a full run.

**Integrity.** The instructions give the first 16 hex digits of the kit's SHA-256. Jon checks the file before using it, and every `RESULT` line repeats the digest, so a pass is always tied to the right kit.

## Layer 3: structure

The `structure` vectors are the automated half. For `scripts/sshcli.py` the expected list is exactly:

| Function | Calls |
| --- | --- |
| `CliSession._spawn` | `pty.fork`, `os.execvp` |
| `CliSession._send` | `os.write` |
| `CliSession.open` | `self._send` (login answers), `os.write` (a space for a paged banner) |
| `CliSession._enable` | `self._send` (`enable` and its secret) |
| `CliSession.run` | `self._send` (the checked command), `os.write` (a space for a pager) |
| `CliSession._cancel` | `os.write` (Ctrl-C) |
| `CliSession.close` | `self._send` (`exit`) |

Every other stage 1 file must have no such call at all. The manual half is in step 10 of the instructions: four greps and one ordering check in `CliSession.run`, readable by eye.

## The read-only guarantee in production

Collection is guarded by independent layers, each checked before production depends on it:

| Layer | Where | Checked by |
| --- | --- | --- |
| Allowlist, deny by default: only `show ...` with display filters, and three session-only `terminal` settings | `readonly.py` | 418 policy vectors, exact regex constants |
| Deny list of state-changing verbs and their abbreviations, as a second line behind the allowlist | `readonly.py` | policy vectors for every verb |
| Character check: no control characters, newlines, tabs, `?` or stray spaces | `readonly.py` | policy vectors |
| Fail closed: a platform with no policy is never contacted | `readonly.py`, `collect.py` | platform, plan and collect vectors |
| One choke point: only `CliSession.run` sends a command, and it checks the policy first | `sshcli.py` | structure vectors, session vectors, manual review |
| Confirmations cancelled with Ctrl-C, never answered; timeouts cancelled before anything else is sent | `sshcli.py` | session vectors against the fake device |
| Plan checked before any device is contacted, and printed | play 1 | plan vectors, the printed plan |
| The code on the execution environment passes the kit before any device is contacted | play 1 | the kit run fails the job |
| Configuration-change marker read before and after | `collect.py` | collect vectors (`configchange` mode exits 3) |
| Every line sent re-checked after the run | `audit.py`, play 4 | audit vectors |
| Every line sent is exactly the plan, in order | `check_facts.py`, play 4 | check_facts vectors |
| Device-side read-only account and command accounting | the devices | Jon, on the canary runs |

The allowlist accepts any `show` command shape, not only the 13 the project sends. That matches the reference. The tighter guarantee in production is the last two software layers: the audit must equal the plan exactly, so a run that sent anything outside the 13 planned lines fails. If you want the policy itself to accept only those exact commands in production, that is a small change to make in the reference first and then carry through the kit; I'd treat it as a separate decision.

The strongest layer doesn't depend on any code: a collection account that the devices themselves only allow to run `show` and `terminal` commands (TACACS+ command authorisation, or a custom privilege level), with command accounting turned on. I recommend having that in place before the first live run (stage 0 of the roadmap).

## Live gates

Each stage goes live in the same steps. Jon sends back the lines listed; nothing else is needed.

| Gate | What runs | Pass | Send back |
| --- | --- | --- | --- |
| G0 | Kit hash check | `sha256sum` starts with the published digest | nothing (a mismatch means the file was damaged in transfer) |
| G1 | `playbooks/conformance.yml` in AWX | Kit `RESULT PASS`, unit tests OK, on the production execution environment | both lines |
| G2 | Play 1 of `gather_topology.yml` | The printed plan matches the instructions word for word | "plan matches" |
| G3 | One canary device | Audit `ok`; `CHECK PASS 1 file(s)`; config check `unchanged`; device-side accounting shows exactly the job log's `sent` lines | audit line, `CHECK` line, `FINGERPRINT` block |
| G4 | A few devices covering every model and IOS release in the estate | As G3, for each | the same lines |
| G5 | All devices of the stage's platforms | As G3; warnings explained | the same lines |

A gate that fails stops the rollout until the cause is understood.

## Layer 7: the fingerprint

`check_facts.py` prints, after its checks, a block describing the shape of all the facts files together: for each JSON path, how many values of each type it saw; for each field with a fixed set of values (interface kind, neighbor protocol, tunnel status, audit status, device role and so on), how many of each; for each list, the total, minimum, median and maximum length; and which raw commands were present. It never prints a hostname, address, interface name, MAC, serial, description or any output. For example:

```text
$.interfaces sizes: total 1180, per item min 4 median 28 max 61
$.interfaces[].kind =: lag=40 loopback=24 physical=960 subinterface=12 tunnel=8 vlan=136
$.interfaces[].mac: null=60 str=1120
$.raw keys: show cdp neighbors detail=42 show interfaces=42 ... show vlan brief=30
```

From this I can see problems the structure check can't: a parser that returns no neighbors on one model, every MAC missing, a command no device supports. I then fix the reference, rebuild the kit and send a patch instruction.

## When something fails

| Symptom | Meaning | What to do |
| --- | --- | --- |
| Kit `FAIL` lines | The rebuild differs from the reference | Paste the lines to Copilot: "change the code so it passes; don't change the kit". Send them to me if it can't. |
| Unit tests fail, kit passes | Usually a test written wrongly | Send me the failing test's name and assertion line. |
| Plan differs | A command list or the policy differs | Stop. Kit `plan` and `constants` sections will also fail. |
| `CHECK FAIL` with a schema problem | The rebuild wrote a different structure from real output | Send the problem lines (paths and rules only). |
| Warnings about names not among the device's interfaces, or `parse_error` | Real output the parsers don't handle | Send the warning lines and the device's model and IOS release. I reproduce it in the reference, fix it there first, rebuild the kit, and send a patch. |
| Audit `FAIL`, or `CONFIGURATION CHANGED` | A read-only layer fired | Stop collection. Check device-side accounting for who changed what. Send me the audit lines. |

**A fix is never made only in production.** Every behaviour change goes into this repository first, with a test, then a rebuilt kit with a new digest, then a short patch instruction for Copilot. Otherwise the two would drift apart and the kit would stop meaning anything.

## Layer 9: comparing both versions on a lab device (optional)

If a lab device can be reached from both an environment running this repository and one running the rebuild, collect it with each and run `python3 conformance/check_facts.py --compare a.json b.json`. It ignores collection times and prints only the path of the first difference. Live output changes between runs (counters, ARP and MAC entries age), so differences there are expected; the device, interfaces, VRFs and addresses should match.

Lab output that can be shared is also the best way to grow the kit: a captured `show` output from each model in production becomes a parser vector, so the kit covers the real formats and not just synthetic ones.

## Limits

- The kit's inputs are synthetic. They cover the formats seen so far, not every IOS release. The fingerprint and the warnings are how real formats it doesn't cover are found.
- Session vectors depend on the fake device behaving as described in the instructions. If the fake device is built wrongly, session vectors fail and the step's instructions say how to fix it; they cannot pass wrongly, because the expected device log is fixed.
- Timing-dependent text (the device transcript after a failed login) is compared only up to its first line.
- No software check can prove a device won't misbehave on a command the policy allows. That's what the device-side read-only account is for.
