# Production rebuild roadmap

Created 2026-10-31 · Status: proposed; stage 1 instructions and kit ready · Reference: `main` a3e6da7

## Goal

Run autotop-awx on the production AWX, with every line of code regenerated by Microsoft Copilot, in stages, until production does everything `main` does today:

- read-only collection from Cisco IOS / IOS-XE over SSH, Palo Alto firewalls over the PAN-OS XML API (directly or through Panorama) and Windows servers over PowerShell and OpenSSH;
- links found from LLDP/CDP, MAC tables and shared subnets, with shared segments and port-channel collapse;
- one format-neutral diagram model, written out by two independent writers, Microsoft Visio (`topology.vsdx`) and draw.io (`topology.drawio`), with node positions kept in a Visio template (`template.vsdx`) and icons read from a folder of PNG files;
- the feature layers: IPsec tunnels, VLANs, firewall zones and server roles;
- the read-only audit and the config-change check on every run.

Each stage adds one slice, is checked offline against a conformance kit built from this repository, and then goes live in gates on real devices. A stage starts only when the previous one is live. The [validation method](production-rebuild-validation.md) describes the checks, and the [stage 1 Copilot instructions](copilot-stage-1-data-gathering.md) are the first set of prompts.

This replaces the [2026-10-25 Copilot rebuild instructions](../2026-10-25/copilot-rebuild-instructions.docx), which rebuilt the whole project in one pass from an older snapshot, before the read-only safeguards, the multi-vendor drivers and the Visio writer existed, and had no way to check the result from outside production.

## How every stage runs

1. **Here:** I write the stage's Copilot instructions and build its kit from this repository (`python3 conformance/build_kit.py <stage>`). Each kit contains all earlier stages' vectors too, so a later stage can't break an earlier one unnoticed. A test in this repository fails if a kit no longer matches the code.
2. **In production:** Jon brings in the instructions and the kit, and checks the kit's SHA-256.
3. Copilot builds the stage step by step. Each step has a kit section to run straight away (`run_kit.py --section ...`).
4. The stage is accepted offline: full kit `RESULT PASS`, unit tests OK, structure review, as an AWX job on the production execution environment (gate G1).
5. Live gates G2 to G5: the plan, one canary device, a few devices per model, then everything.
6. Jon sends back the result lines (counts, rule names, digests and the fingerprint: no device data). I review them before the next stage.

If production shows something the reference doesn't handle (an IOS release whose output a parser misreads, say), the fix goes into this repository first, with a test and a rebuilt kit, and then into production as a short patch instruction. Production and the reference never diverge.

### Stage 0: prerequisites

- **A production Git repository** that AWX uses as the project source, and a way to bring a document and one JSON file into the environment where Copilot runs.
- **The AWX execution environment:** Python 3.9 or later, the OpenSSH client (`ssh`), and `ansible.builtin` only. No compiler is needed until stage 5.
- **A read-only collection account** on the devices. Best: TACACS+ command authorisation that permits only `show *` and `terminal length 0`, `terminal width *` and `terminal datadump`, with command accounting on. At minimum: a local account whose privilege level can run the planned commands, including `show running-config | include configuration change` (if it can't, the config check reports `unavailable` as a warning, and collection still runs).
- **An AWX credential** of the built-in "Network" type for that account.
- **Canary devices:** one switch to start with, then one of each model and IOS release in the estate.
- **The artifact server** (optional in stage 1): if the facts files should be copied off the AWX job container, its host and destination path (`artifact_facts_dir`).

### Stage 1: read-only data gathering, Cisco IOS / IOS-XE

Instructions: [copilot-stage-1-data-gathering.md](copilot-stage-1-data-gathering.md). Kit: `conformance/stage1/kit.json`.

Differences from `main`, all deliberate and covered by the kit:

- Only the `ios` platform has a driver and a read-only policy. PAN-OS and Windows hosts are refused before anything connects, because their policies don't exist yet.
- `commands.py` reads the facets to collect from a fixed table instead of the feature plugins (which arrive in stage 6). It produces the same 10 commands.
- `config.py` holds only `ENABLED_FEATURES`.
- The collection playbook has four plays: check (now including a kit run, so code that doesn't conform never contacts a device), collect, copy facts to the artifact server, audit and check. Stages 5 and 7 add the build and publish plays.
- `drivers.load()` and `reparse()` (upgrading old facts files) come with stage 4, when files are first read back.

### Stage 4 note: `parser.py` must be renamed

On Python 3.9, `parser` is a built-in module, so `import parser` gets the interpreter's own deprecated module instead of `scripts/parser.py`, whatever `sys.path` says. In this repository, 52 tests fail on Python 3.9 for that reason (they pass on 3.10 and later, where the built-in module is gone). If the production execution environment runs Python 3.9, `main.py` would fail in the same way. Before stage 4 the reference should rename the module (for example to `facts.py`) and the stage 4 instructions will use the new name.

### Stage 5 decision: the C extension

The link router's search loop is C (`scripts/csrc/_hanan.c`), committed as a prebuilt binary (`_hanan.abi3.so`) so AWX needs no compiler. A binary can't be "regenerated by Copilot". The options will be: Copilot regenerates the C source and it is compiled once in a build environment with a compiler (`python3 scripts/build_ext.py`), and the binary committed to the production repository; or production uses the pure-Python router (`pathfinder.astar_route_py`, which the C version must match route for route), which is slower on large diagrams. I'll ask before stage 5.

## What I need back from each stage

Only lines that hold no device data:

- the kit's `RESULT` line and the unit tests' summary line, from the production execution environment;
- "plan matches" for G2;
- for each live run: the audit summary line, the `CHECK` line, the `FINGERPRINT` block and any problem or warning lines (they name JSON paths and rules, never values);
- for a parser warning: the device's model and software release.
